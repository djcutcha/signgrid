# 評価の設計

看板の安全判定(1〜4 のランクと、点検項目ごとの判定)を AI がどれだけ当てるかを測る仕組みの説明。
正解データの実体はこのリポジトリに入れない(参照先のパスだけ `data/private/sources.toml` に書く。雛形は `data/private/sources.example.toml`)。

## 1. 共通の軸

各社の様式はランクの書き方が違う(A〜D、良好〜即時修理、◎○△×)。評価では次の4段階にそろえる。

| 値 | 意味 |
|---|---|
| 1 | 良好 |
| 2 | 経過観察 |
| 3 | 要改善 |
| 4 | 即時対応・危険 |

「要対応」= 3 または 4。見逃しを最も重く見る(危険な看板を「大丈夫」と言わないこと)。

## 2. 正解データ(看板1基 = 1レコード)

統一形式 `EvalItem`(`kanban_karte/eval/dataset.py`):

| 項目 | 内容 |
|---|---|
| source | paper_scan / xlsx_center / xlsx_karte / xlsx_sketch / xlsx_compliance |
| sign_id | 看板を一意に指す ID |
| photo_paths | 入力になる画像(実在するファイルだけ) |
| rank_true | 正解ランク 1〜4。無ければ None |
| item_judgments_true | 項目ごとの正解 {項目名: 1〜4}。無ければ None |
| split | eval(評価用)/ example(例示用) |
| meta | 点検日など。評価には使わない |

### ソース別の扱い

| ソース | 中身 | 正解ランクの取り方 | 項目判定 |
|---|---|---|---|
| paper_scan | 紙の点検・完成報告書のスキャン束。入力は完成報告書ページから切り出した写真セル(下記) | 用紙の評価欄を、用紙の凡例で 1〜4 に直した値。凡例が読めない用紙・調査票様式は空(除外) | なし |
| xlsx_center | 客先A: センター単位の安全点検報告書(Excel)。看板ごとに18項目 | 看板別の腐食・破損・固定(A〜D)の最悪値。センター総合評価は同じセンターの看板が共有するため使わず meta に残す | 18項目(②腐食/破損/固定の A〜D と、④の良好/経過観察/要改善) |
| xlsx_karte | 客先B: 看板カルテ様式(Excel)。5項目×4段階 | 5項目のうち最悪の値(様式に看板単位の総合欄が無いため、派生値) | 5項目 |
| xlsx_sketch | 客先C: Excel 様式(写真と項目のみ) | 判定欄が全て空 | なし。評価対象外。写真は入力例にだけ使える |
| xlsx_compliance | 客先D: 条例の適合/不適合の調査 | 安全ランクではないので付けない(meta の compliance に適合/不適合) | なし。法規判定の正解として別枠 |
| line_paper | 客先の 2026年 1店舗(LINE 写真+手書きの点検票スキャン)。評価 829 基には入れない手付かずの検証セット(`--source all` に含まれない。`--source line_paper` で指定) | 点検票(D=◎ 経過良好 … A=× 危険、paper_scan と同じ凡例。D→1, C→2, B→3, A→4)の判定欄を Sonnet 5.5 で転記し、判定のあるセルの**最悪値**を看板の総合ランクにする(様式に総合欄が無いので xlsx_karte と同じ派生値)。1 看板= 写真フォルダ 1 つ+点検票 1〜2 頁。分割は看板単位 | 点検票の行(部位×点検内容)。看板ごとに行が違うので、項目一致率は他のソースと比べない |

項目判定から外すもの: 対象外、未記入、複数印(「良好/経過観察」など1項目に2つ印)、読み取れない書式。外した複数印の数は meta に残す。

### 紙の束は写真セルの切り出しだけを入力にする(評価欄が写るため)

完成報告書のページは、写真のほかに、評価ランク欄(◎○△×)、看板名の帯、総評(所見)欄、写真ごとのキャプション欄を持つ。paper_scan の正解ランクは、まさにその評価欄から読み取った値である。ページ画像をそのまま AI に渡すと、AI は看板の状態を判定するのではなく、用紙に書かれた答えを読むことになり、測定が成り立たない。総評やキャプション(「錆あり」「汚れあり」など)も、点検者の所見そのものである。

そのため、AI に渡すのは**写真が貼られた矩形だけ**を 1 枚ずつ切り出した画像にする(`kanban_karte/eval/crop.py`)。

- 画素の統計だけで検出する(OCR も外部 API も使わない)。左右 2 面付けのページは中央で分け、面ごとに「白でない画素」の密度が高い連続行を写真の行、行の中の密度の高い連続列を写真のセルとする。ヘッダの文字行・評価欄・写真下のキャプション欄は密度が低いので入らない。
- 白い空などで検出が欠けた段・列は、同じ面の他のセルの上下・左右にそろえて広げる。上へ広げるときは、ヘッダ帯と前の段のキャプション欄に入らない範囲に限る。
- 写真の下に黄色いマーカーで強調したキャプション帯があれば、その分を削る。下端は常に 10px 削る。
- 横向き・上下逆に取り込まれたページは `page_index.tsv` の回転角で起こしてから検出する。
- 空の写真枠(白い枠)・手書きの記入例だけのページからは何も出ない。1 枚も切り出せない看板は AI 評価から除外し、件数を結果に載せる(どの判定役も同じ母数で比べるため、constant・oracle でも同じく除外する)。
- 切り出した画像は `data/private/crops/` に置く(未追跡。検出ロジックを変えたらバージョン `CROP_VERSION` を上げる)。
- 確認: 切り出した全画像(300dpi 版 2609 枚を含む)に文字認識(Mac 内蔵、外部 API なし)をかけ、「評価ランク」「総評」「点検者」「申請No」「写真No」と、写真の下端にあるキャプションの文字が残っていないことを確かめた。写真に写っている看板・標識の文字は、写真そのものの内容なので残る。目視確認用に `tools/overlay_crops.py`(検出した枠を重ねた画像を作る)がある。
- 入力画像: 元の PDF(`pdf_root` に `<束id>.pdf`)の各ページはスキャン画像 1 枚の埋め込みなので、描き直さずにその画像(約 300dpi、A4 で 3507×2480px)をそのまま取り出す。ページの `/Rotate` を反映した向きにそろえ、検出は 90dpi 相当に縮小した画像で行って、座標を元の画像に戻して切り出す(検出の閾値が 90dpi 基準のため)。切り出した写真は長辺 1600px を上限にして保存する。PDF が無い束は 90dpi のページ画像で代用する(幅 300px 前後と小さい)。
- 切り出し後の大きさ(2026-11-02、評価対象の 320 基のうち切り出せた 314 基・2609 枚): 幅は最小 377px、10 パーセンタイル 950px、中央値 957px、90 パーセンタイル 993px、最大 1074px。
- 限界: 写真の白い部分が多いセルは、枠が写真より小さく検出されることがある(中身は写真の一部)。写真の枚数・並びは用紙の様式に依存する。

### 注意(独立な標本ではない)

- xlsx_karte は同じ看板が点検年ごとに複数回出る。
- xlsx_center は同じセンターの看板が写真の撮り方や様式を共有する。
- 判定は点検者の自己申告で、第三者の正解ではない。「点検者との一致率」であって「真実との一致率」ではない。
- 正解の偏りが大きい(xlsx_center は看板別ランクの約79%が 1、xlsx_karte は約73%が 1、paper_scan は約66%が 2)。「常に 2 を返す」判定役でも paper_scan で約6割当たるため、AI の数字は必ず定数判定役と並べて読む。

## 3. 評価用と例示用の分割

- 決定論: 分割キーの SHA-256(塩つき)の下位64ビットを 100 で割った余りが 70 未満なら評価用(eval)、それ以外は例示用(example)。実行のたびに変わらない。
- 例示用は、AI に見せる例(few-shot)や規則の調整に使ってよい側。評価用は測定専用で、中身を見て調整しない。
- 分割キーは現場単位。paper_scan は束(同じ現場の報告書1束)、xlsx_center はセンター、xlsx_karte は会館。同じ現場の看板、同じ看板の年違いが評価用と例示用に割れない。
- ランクが無い看板も分割は付くが、評価母数と件数表(ランクありだけ)には入らない。

## 4. 指標

予測 `Prediction` は rank_pred(1〜4 または None)、item_judgments_pred、confidence、raw。

| 指標 | 定義 |
|---|---|
| 評価母数 n | 正解ランクがある看板の数。正解ランクが無い看板は除外し、除外数を必ず併記する |
| 完全一致率 | rank_pred == rank_true の割合 |
| ±1以内 | abs(rank_pred − rank_true) ≤ 1 の割合 |
| 見逃し率 | 正解が要対応(3,4)の看板のうち、予測が要対応でなかった割合(= 1 − 再現率)。最重要 |
| 誤警報率 | 正解が要対応でない看板のうち、予測が要対応だった割合 |
| 要対応の適合率 | 予測が要対応の看板のうち、正解も要対応だった割合(補助) |
| 混同行列 | 4×4。行=正解、列=予測 |
| 項目一致率 | 正解の項目判定(上の除外後)のうち、予測が同じ値だった項目の割合。判断できず(予測が null・欠落)は不一致に数える。答えた項目だけの率も併記 |

- 予測が None(判定できず)は、完全一致・±1 では不正解、正解が要対応なら見逃し。正解が要対応でなければ誤警報にはならない(警報を出していない)。
- **判断できず**は別枠で数える。看板単位 = ランクを返せなかった看板数。項目単位 = 正解のある項目に予測が値(1〜4)を返さなかった数(null または欠落。項目判定を返さなかった看板の項目も含む)と、1 項目以上が判断できずの看板数。一致率は 2 通りを併記する: 判断できずを不一致に数える率(基本)と、答えたものだけの率。
- 正解ランクがない看板、入力の写真が 1 枚もない看板は、評価母数から除外して件数を併記する。
- 分母が 0 の指標は n/a(None)。0% とは書かない。
- 全体の数字は3ソースの看板を単純に合算する。ソース別の数字も必ず見る。
- **見逃し(写真可)**: 要対応(正解 3・4)を、正解の項目判定で 4 区分に分ける。a = 項目の内訳なし(総合だけ)、b = 内訳はあるが 3 以上の項目なし、c = 3 以上の項目があり、写真で判定できる項目を含む、d = 3 以上の項目が全て写真で判定できない項目(項目名に 球切れ・点灯・内部・電気 を含む)。「見逃し(写真可)」は c だけを母数にした見逃し率で、a・b・d は写真で勝負できるとは言えないので母数から外す。a は何が要対応だったか分からず、b は正解側の項目に要対応の根拠が無く、d は昼の写真では見えない(見えない物は見えない)。分類は正解の項目名の語による機械判定で、c にも写真に写らない原因が混じりうる。Day2 全量(829基・例示6)の要対応 90 基は a 37 / b 23 / c 28 / d 2。c の見逃しは Opus 5.5 が 22/28(78.6%)、Sonnet 5.5 が 23/28(82.1%)で、総合の見逃し率(Opus 69/90=76.7%、Sonnet 65/90=72.2%)とは母数が違う。

## 5. 判定役(Judge)

`judge(item) -> Prediction` の差し替え式。`constant` と `oracle` は測定スクリプトの検算用、`claude` が AI 判定役(下記)。

- `constant`: 常に 2(経過観察)。項目判定は、その様式の項目に全て 2 を入れる(項目一覧は様式で既知のため)。AI を入れる前の下限の目安。
- `oracle`: 正解をそのまま返す。一致率 100%・見逃し 0 になるはずで、ならなければ測定側のバグ。この数字を評価結果として報告しない。

### ClaudeJudge(`kanban_karte/eval/claude_judge.py`)

Claude に写真を見せて判定させる。既定は**ゼロショット**(例示なし)。`--examples N`(0〜6)で例示つき(few-shot)になる。

- 例示(v2): 同じ様式(source)の例示用(split="example")から最大 N 基を「有資格者の過去の判定例」として、メッセージの先頭に置く。評価用の看板は絶対に入れない。選び方は決定論: 正解ランク 1・2・3・4 を 1 基ずつ(無いランクは飛ばす)、残りは 1 と 2 を交互に足す(ゼロショットの外れが「正解1→予測2」に集中しているため、同じ様式の 1 と 2 を必ず対で入れる)。同じ現場から重ねない。6 基なら 1,1,2,2,3,4。各基の写真は最大 3 枚(等間隔)で、正解のランクと項目判定を付ける。看板名・現場名は伏せる(「例1」「例2」)。正解データに所見(自由記述)の欄は無いので、所見は付けない。
- 見逃し対策(`--guard`): システムプロンプトに「要改善・即時対応を見落とすことが最も重い誤り。腐食・緊結部のゆるみ・ひび・傾きの兆候があれば 3 以上を検討し、根拠を evidence に書く」を足す。甘い側へは誘導しない: 同じ文に「写真に兆候が見えないのに念のためで上げない」と書き、誤警報率も同時に見る。出力は項目ごとに `{"rank": 1〜4|null, "evidence": 「どの写真の何を見たか」1文, "needs_onsite": bool}` になる。`needs_onsite=true`(写真では判定できない= 要実測・対象外)は null と同じ「判断できず」として項目の値に入れない(不一致に数える率と答えた分の率は既存どおり)。evidence と needs_onsite は結果 JSON の看板ごとの `item_notes` に残り、`needs_onsite_items` に合計が出る。項目一覧のない様式(紙の束)は根拠を reasons に書かせる。
- ルーブリック(`--rubric`): ある客先の評価基準(a〜d の4段階と、部位ごとの判定ポイント)の要点を、システムプロンプトの規則部に文字で入れる(a=1〜d=4 の目安。見本写真は送らない)。原本は eval 側の rubric.md で、リポジトリには要点の転記だけ(顧客名・単価は書かない)。様式の項目名と判定例があればそちらを優先させる。
- prompt caching: 例示ブロックを先頭に固定し、最後のブロックに `cache_control` を付ける。例示は様式ごとに別なので、様式の最初の 1 基だけ単独で流してキャッシュを作り、残りを並列にして読み出させる。使用量はキャッシュ書き込み・読み出しを分けて記録し、費用は書き込み 1.25 倍・読み出し 0.1 倍で計算する(倍率は仮置き。請求で要確認)。

- 送る物: 写真(1 看板あたり最大 6 枚、既定。`--max-photos`)を長辺 1280px の JPEG に縮小したもの、看板名、様式の項目名一覧(分かる様式のみ)。現場名・点検日・正解は送らない。写真が 0 枚の看板は API を呼ばず「判定できず」にする。
- システムプロンプトに、共通軸の 1〜4 の定義と JSON 形式を書く。看板のランクは項目判定の最悪値、写真から分からない項目は null(推測しない)。
- 出力 JSON: `{"rank": 1〜4, "items": {項目名: 1〜4 または null}, "reasons": [...], "confidence": 0〜1}`。`rank` が整数 1〜4 でない、項目値が 1〜4 でも null でもない、`confidence` が 0〜1 でない、JSON が壊れている、のどれかなら不正。不正なら、不正だった応答と指摘を付けて **1 回だけ**再試行し、それでも不正なら `rank_pred = None`(判定できず)にして、生の応答を結果 JSON の `raw` に残す。
- モデルは `--model`(既定 `claude-sonnet-5-5`)。サンプリングパラメータ(temperature など)は送らない: 現行のモデルは既定値以外を受け付けず、SDK 2.x には引数自体が無い。決定性は「毎回同じ入力・同じ設定」でしか担保できないので、同じ看板を複数回流して揺れを測る場合はそのつもりで。`--effort` で思考の深さ(output_config.effort)を指定できる(省略時は API の既定)。
- 並列は最大 4 本(`--workers`)。429・529・5xx・接続エラーは SDK が指数バックオフで再試行する(最大 6 回)。使い切ったら、その看板は判定できず。401・403(鍵・権限)は全件失敗するので実行ごと止める。
- 鍵: 環境変数 `ANTHROPIC_API_KEY`。リポジトリ直下の `.env` も読む(`.env.example` に変数名だけ)。`.env` は git に入れない。
- 結果 JSON に看板ごとの入力・出力トークン、試行回数、推定費用、全体の合計が入る。`runs/latest.md` にも合計トークンと件数が出る。費用は価格表(`PRICES`)による推定で、請求額ではない。
- `--dry-run`: API を呼ばず、送る看板数・写真枚数・推定入力トークンと概算費用だけ出す(鍵は要らない)。

## 6. 実行

```
python3 -m kanban_karte.eval.run_eval --judge constant --source all
python3 -m kanban_karte.eval.run_eval --judge oracle --source xlsx_karte --limit 50
```

- `--source`: all / paper_scan / xlsx_center / xlsx_karte(all は3つ)
- `--split`: eval(既定)/ example / all
- `--limit N`: ソースごとに N 件。`--seed`(既定 0)で決まる決定論のランダム抽出。正解ランクのない看板は抽出の前に除く
- `--append-log`: 結果の 1 行を、このファイル末尾の「日ごとの測定記録」の表に追記する(`--log-note` で条件欄に一言足せる。oracle は不可)
- `--judge claude` のとき: `--model` `--max-photos` `--workers` `--effort` `--examples` `--guard` `--rubric` `--dry-run`
- `--out`: 結果 JSON(省略時 `runs/YYYY-MM-DD_HHMM_<judge>.json`)。同じ場所に `latest.md` を書く
- 結果 JSON には看板ごとの正解と予測(sign_id 入り)が入る。Markdown 要約は件数と率だけ。`runs/` は git に入れない
- テスト: `python3 -m unittest`

### 近接パス(`kanban_karte/eval/closeup.py`)

第1パスが 1・2 とした看板の写真を、元解像度から 2×2 のタイル 4 枚+全景 1 枚(各長辺 ≦1280px、拡大はしない)にして再判定させる。1 基あたり写真は最大 2 枚(第1パスの reasons が「写真N」と挙げた番号を優先)。総合ランクは項目の最悪値(項目のない様式はモデルの総合)。`--select-out` で本丸(区分 c の見逃し)と対照(正解 1・2 を第1パスが正しく 1・2 とした看板、本丸と同じ様式の基数を seed=1 で抽出)を選び、`--closeup-targets` / `--closeup-out` で回す。

2026-11-02 の測定(Opus 5.5、44基= 本丸 22+対照 22): 本丸で救えた 0/22、動かなかった 22/22、対照の誤警報 0/22、費用 $1.11(入力 134,060 トークン)。ただし**縮小仮説の前提が成り立たなかった**: 全 4,267 枚(各看板の先頭 6 枚)のうち長辺が 1280px を超えるのは 10 枚だけで、対象 44 基の使用写真 88 枚は全て長辺 1012px 以下(中央値 552px)。第1パスでも縮小は起きておらず、タイルは同じ画素の切り出しにすぎない。この結果は「縮小で消えた劣化」が無いこと(と、切り出しで注意を寄せても見えないこと)を示すにとどまり、写真の解像度そのものが足りない可能性は否定できない。

- confidence が mid の基の誤差の中央値は 7〜10%、low は 20〜25%。low を「要実測」寄りに扱う根拠にはなる。

### 2 枚の合わせ方の比較(2026-11-04、Sonnet 5.5、20 基×2 枚、40 呼び出し、$1.13、測定 1 回でゆらぎ未確認)

|---|---|---|---|---|
| 写真1だけ | 49.7% | 29/40 | 22.8% | 14/40 |
| 写真2だけ | 55.3% | 24/40 | 23.3% | 13/40 |
| 交差(2 枚の範囲が重なる部分) | 32.3% | 16/40 | 20.4% | 18/40 |

結論: 2 枚を 1 回で送る方式を続ける。2 枚を別々に推定すると、20 基とも範囲は重なったが、交差にすると範囲に正解が入る数が 16/40 に落ちる(2 枚は互いに独立でなく、同じ物差しの仮定で同じ向きに外す)。和集合は外しにくいが範囲が広く、法規の判定が両端で割れて要実測が増える。相対誤差の中央値と ±15% 以内も、1 回で送る方式が最良。
