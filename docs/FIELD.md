# 一周の実測(客先の 2026年 1店舗: LINE 写真+手書き点検票)

実在の 1 店舗の点検一式(2026-08-31 点検)を、今の SignGrid にそのまま通して「一周」した記録。評価 829 基には入っていない店なので、手付かずの検証セットとして記録表(EVAL.md)に `line_paper` として足した。店名・客先名・点検者名は書かない。写真・点検票・台帳・出力はリポジトリに入れない(置き場は `data/private/sources.toml` の参照だけ。台帳と画面写真は未追跡の `data/private/`・`runs/`)。

## 入力

| 物 | 量 |
|---|---|
| 写真(LINE アルバム、長辺 1,477px、EXIF なし) | 1,398 枚、86 フォルダ(通常看板 23 + その他看板 63。1 フォルダ 1〜200 枚) |
| 点検票スキャン(200dpi、手書き) | 3 本 140 頁(通常 25・その他 52+63) |
| 配置図・KY | 配置図は看板の位置の番号だけ、KY は作業報告書。どちらにも番地の記載はなく、住所は「東京都杉並区」まで(`data/private/field_site_address.txt`、未追跡) |

## 手順

1. `tools/field_transcribe.py --run --verify`: 点検票の頁画像を Sonnet 5.5 で JSON に転記(部位・点検内容・D/C/B/A/対象外/空・寸法)。15 頁(通常 5・その他 10)は Opus 5.5 でも転記して照合する。出力は置き場の外(正解データ側)の `transcribed/`。
2. `tools/field_index.py`: 写真フォルダと転記の看板番号を突き合わせ、索引 `index.tsv` と正解表 `items.tsv` を作る(API なし)。
3. `tools/field_run.py`: 新しい台帳を作り、(a) PDF 3 本を束として登録 (b) 看板と写真(撮影順の先頭 6 枚)を登録 (c) `pipeline/draft.py` で全基の下書き(Opus 5.5、承認済み規則なし) (d) 東京都 第2号様式と客先A型 xlsx を書き出す。工程ごとの秒数と費用は `runs/field_site_run.json`。
4. `run_eval --judge claude --model claude-opus-5-5 --source line_paper --examples 6`: 評価の指標を記録表に 1 行足す。
5. `python3 -m kanban_karte.web --db data/private/field_site.sqlite` で確認画面、`tools/web_screenshots.py --only field --out runs/field_site_img/` で画面写真(PC/SP)。

### 判定の数字(評価側 47 基。Opus 5.5、写真 6 枚まで、例示 6)

| 指標 | `run_eval`(line_paper) | 製品の下書き(同じ 47 基) |
|---|---|---|
| 完全一致 | 70.2%(33/47) | 61.7%(29/47) |
| ±1 以内 | 97.9% | 100% |
| 要対応(3,4)の見逃し | 5/9 | 7/9 |
| 誤警報 | 1/38 | 1/38 |
| 項目一致 | 49.0%(答えた項目だけ 67.1%)。点検票の行との比較 | 比べない(18 項目の様式と点検票の行は別物) |

同じ判定役(Opus 5.5)なので近い値になるはずだが、差がある。理由は 2 つ: (1) 例示の出どころ。下書きは客先A の看板、`run_eval` は同じ店の看板(例示用の側の 6 基)。(2) 判定の様式。下書きは 18 項目、`run_eval` は点検票の行。要対応は 9 基しか無く、見逃しの 5 と 7 の差は 2 基分なので、差の大きさは 1 店舗の標本では決めきれない。どちらも**要対応を半数以上見逃す**。下書きの混同行列では、正解 3 の 15 基のうち 12 基を 2(経過観察)と答えている(全 67 基)。全 67 基(写真あり・評価側と例示側)の下書きでは、完全一致 64.2%、見逃し 12/15。

## スケッチからの寸法と法規

点検票の PDF は「清書の表(看板番号あり)→ 次頁に手描きスケッチ(番号なし。印刷案を貼った頁もある)」の対でできている。スケッチを前頁の看板に結び付け、寸法と取付方法を台帳に入れ、面積・全高で法規の判定を通した。

1. `tools/field_sketch.py`: 同じ PDF で「番号のある頁 n」の直後の「番号のない頁 n+1…n+k」をその看板のスケッチとする(通常・その他1・その他2 とも同じ規則)。頁画像(長辺 2,000px)を Sonnet 5.5 に読ませ、`w_mm h_mm d_mm gl_mm gl_edge(bottom/top/unknown) post mount display_text printed confidence raw_notes` を取る。表の size と突き合わせ、食い違いは両方残す。出力は置き場の `transcribed/sketches.jsonl`(リポジトリの外)。
2. `tools/field_index.py`: `items.tsv` に `sketch_pages sketch_w_mm sketch_h_mm sketch_gl_mm sketch_gl_edge post mount sketch_confidence` を足す(スケッチの無い看板は空)。
3. `tools/field_legal.py`: 面積 = W×H、全高 = GL の縁が bottom なら gl + h、top なら gl、unknown なら出さない。住所は区まで(用途地域・看板の種類は渡さない)。

| 対応付け | 数 |
|---|---|
| 番号のない頁 | 57(通常 3・その他1 24・その他2 30) |
| 看板に付いた頁 / 付かなかった頁 | 57 / 0(看板 53 基) |
| うちスケッチの頁(寸法線・図あり) / 図なしの頁 | 47 / 10(印刷案だけの頁 6、番号が読めなかった表の頁 1、書き込みだけ・白紙 3) |

| 抽出(看板 53 基) | 基数 |
|---|---|
| W・H が取れた | 33 |
| GL が取れた | 23(縁 bottom 4・top 8・unknown 11) |
| 取付方法が取れた | バンセン 5・ビス 3・吊り 3(不明 42) |
| 印刷案の貼付あり | 28 |

表の size との一致(相対差 3% 以内): W 32/35、H 29/35、GL 6/8(両方に値がある頁だけ)。食い違いは表の転記の読み違い(GL 145 と 1450 等)、スケッチ側の読み違い、全体寸法と看板本体の取り違えの混在で、どちらが正しいかは紙に戻らないと決まらない。

| 法規(74 基、東京都条例、自家用) | スケッチ前 | スケッチ後 |
|---|---|---|
| 面積が出た基数 | 68 | 71 |
| 全高が出た基数 | 0 | 12(最大 9.3m、4m 超 2 基) |
| 許可 不要 / 要 / 要実測 | 64 / 4 / 6 | 67 / 4 / 3 |
| 管理義務 要 | 74 | 74 |
| 点検の義務 不要(条例に規定なし) | 74 | 74 |
| 有資格者 不要 / 要実測 | 64 / 10 | 67 / 7 |
| 行政への報告 不要 / 要実測 | 64 / 10 | 67 / 7 |

要実測は 6 基から 3 基に減った(3 基はスケッチに W・H が読めた看板)。残る 3 基の理由は寸法なし(表にもスケッチにも W×H が無い)。GL 不明・区分なしが理由で残った基数は 0。有資格者・行政への報告の要実測 7 基は、許可が要実測の 3 基と、許可が「要」の 4 基(看板の種類が分からない)。全高は許可の結論を 1 基も変えなかった(この住所の許可は面積だけで決まる)。W・H の優先を表からスケッチに入れ替えても、許可の結論は変わらない。API 費用は Sonnet 5.5 で $0.80(試し読みの $0.07 を除く)。

## 画面

`runs/field_site_img/` に PC/SP の台帳一覧・カルテ 1 基(黄色あり)・様式出力(`field-ledger|karte|output-pc|sp.png`)。顧客の写真が写るので `docs/img` には置かない。

## 限界

- 正解は紙の判定を AI が転記した物。転記の照合は 15 頁で、判定の並びの一致 95.1%(読み違いが 5 件)。総合ランクは最悪値の派生で、紙に総合欄は無い。
- 1 店舗・47 基。要対応(3 以上)は 9 基、4 は 0 基。率の信頼区間は広い。
- 評価の例示は同じ店の別の看板(30%)なので、同じ現場の特徴が例示に入っている。他の店へ一般化した数字ではない。
- 点検票の様式は通常/その他の 2 種で、部位・点検内容の名前が看板によって揺れる(例: 取付方法の「各種取合」の書き方)。項目単位の比較は行っていない。
